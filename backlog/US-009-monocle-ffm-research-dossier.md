# Monocle JNI-to-FFM plan: research dossier (2026-09-22)

Generated from four read-only research agents over C:/SourceCode/jfx-ffm (branch ffm/graphics). Every claim cites file:line in the tree. The plan itself is in the session transcript; this file holds the evidence.

## libc / udev / EPD layer

### Summary

The libc/udev/EPD layer of Monocle is 97 native declarations (LinuxSystem 46, EPDSystem 44, Udev 5, C 2) implemented by 829 lines of C in modules/javafx.graphics/src/main/native-glass/monocle/{linux/LinuxSystem.c,linux/Udev.c,util/C.c,epd/EPDSystem.c,Monocle.h}. None of it is built: native/linux.cmake:148-184 defines only glassgtk3, prismSW, prismES2 and iio, so NativeLibLoader.loadLibrary("glass_monocle") (LinuxSystem.java:64) and loadLibrary("glass_monocle_epd") (EPDSystem.java:329) throw UnsatisfiedLinkError for every LinuxPlatform subclass today (LinuxPlatform.java:32, X11Platform.java:36, EPDPlatform.java:37); the Linux maven-jar-plugin profile additionally strips com/sun/glass/ui/monocle/** from the shipped jar (pom.xml:444-475). Triage: every C function is WRAPPER (a single libc call: open/close/read/write/lseek/mkfifo/setenv/sysconf/ioctl/dlopen/dlsym/dlclose/dlerror/strerror/mmap/munmap/socket/setsockopt/bind/recv) or PURE (struct field get/set on input_absinfo and fb_var_screeninfo, _IOC request arithmetic, JNI NewDirectByteBuffer/GetDirectBufferAddress, udev header-format sniffing). Not one function is OS-CALL in the sense of needing C: the OS symbols are all in libc and bind directly through Linker.nativeLinker().defaultLookup(), the house pattern of FontConfigNative.Libc (FontConfigNative.java:602-650) and GtkGlassNative.Loader (GtkGlassNative.java:5638-5684). libudev is NOT used anywhere: Udev.c speaks the NETLINK_KOBJECT_UEVENT protocol itself (socket/bind to multicast group 2, recv, hand-parsed libudev monitor header; Udev.c:32-37, 42-85, 106-149). Recommended outcome: delete all four C files (and Monocle.h once the X11/EGL lens no longer needs monocle_returnInt/Long, which only x11/X11.c still uses), replace with one package-private FFM facade (proposed com.sun.glass.ui.monocle.LinuxSystemNative) plus StructLayouts, keep LinuxSystem/EPDSystem/Udev/C as thin Java delegates so the ~30 call sites and the LinuxSystemShim keep compiling. All kernel structs in this lens are fixed-width (__u32/__s32/__u16) and arch-neutral; the architecture-sensitive points are exclusively libc parameter types (unsigned long ioctl request, size_t/ssize_t counts, off_t offsets, void* handles) and must come from Linker.canonicalLayouts(), as FTNative.java:425 already does.

### Inventory

- **LinuxSystem.open/close/read/write/lseek/mkfifo** (6 natives)
  - Verdict: WRAPPER (PARITY: exact)
  - Replacement: Direct libc downcalls via Linker.nativeLinker().defaultLookup(): open(ADDRESS path, JAVA_INT flags [, JAVA_INT mode]) declared with Linker.Option.firstVariadicArg(2) because glibc's open is variadic (x86_64 SysV needs %al set for variadic calls; the JDK linker only does that when told) and returns JAVA_INT (the Java API returns long fd; widen in the delegate); close(JAVA_INT)->JAVA_INT; read/write(JAVA_INT, ADDRESS, size_t)->ssize_t where size_t/ssize_t are LINKER.canonicalLayouts().get("size_t")/("long"); the ByteBuffer+position+limit form becomes MemorySegment.ofBuffer(buf).asSlice(position, limit-position) (the C did data+position, limit-position: LinuxSystem.c:70-80); lseek(JAVA_INT, off_t, JAVA_INT)->off_t with off_t = canonical long on LP64 (on 32-bit glibc off_t is 32-bit unless _FILE_OFFSET_BITS=64; bind lseek64/mmap64 if armv7 stays a target); mkfifo(ADDRESS, JAVA_INT mode_t)->JAVA_INT. Path strings via arena.allocateFrom(String) (standard UTF-8; the C used GetStringUTFChars modified UTF-8 - no path here can contain NUL or supplementary characters legitimately). read() blocks on an evdev fd in LinuxInputDevice.run (LinuxInputDevice.java:129-167) on its own daemon thread: an ordinary downcall, never critical(true).
  - Risks: Blocking read() during device removal: JNI returned -1/EIO after close; FFM behaves identically (kernel semantics), but the thread teardown path should be exercised in a child-JVM test. Slicing throws IndexOutOfBoundsException where the C silently computed a huge size_t when position > limit (LinuxSystem.c:73 casts limit before subtracting) - a benign hardening, but record it. setenv/mkfifo/O_NONBLOCK/I_FLUSH/ENXIO/EAGAIN/S_IRWXU have no production caller: only tests/system LensUInput.java:65-282 via LinuxSystemShim.
  - Evidence: LinuxSystem.java:77-118,265; LinuxSystem.c:52-85,150-156; callers LinuxInputDevice.java:86,134; LinuxAbsoluteInputCapabilities.java:80,88; LinuxFrameBuffer.java:50,56,167; EPDFrameBuffer.java:132,217,242,664; EPDInputDeviceRegistry.java:142-143 (opens devNode and never closes or uses the fd: a pre-existing leak, keep as-is in the migration commit); MX6Cursor.java:116,148,186-187; includes LinuxSystem.c:31-41 are libc only.

- **LinuxSystem.ioctl(long fd, int request, long data)** (1 natives)
  - Verdict: WRAPPER (PARITY: exact)

  - Replacement: libudev is not loaded today: Udev.c includes only errno/stdlib/string/linux/un/netinet/in/unistd/sys/types/sys/socket/linux/netlink (Udev.c:29-37) and opens the kernel uevent netlink socket itself. ### Design

- One facade, no C: add package-private final class com.sun.glass.ui.monocle.LinuxSystemNative holding Linker.nativeLinker(), LINKER.defaultLookup() for libc, all static final MethodHandles (invokeExact), the StructLayouts (INPUT_ABSINFO 24, FB_BITFIELD 12, FB_VAR_SCREENINFO 160, SOCKADDR_NL 12, UDEV_HEADER_A/B views) and the only restricted calls (defaultLookup, reinterpret). Model it on FontConfigNative.Libc (FontConfigNative.java:602-650: downcall(name, descriptor) throwing UnsatisfiedLinkError naming the symbol) and ScreencastNative.bind (ScreencastNative.java:584-590: BOUND map of library!symbol for tests). javafx.graphics already carries --enable-native-access=javafx.graphics (pom.xml:354) and the tests' addExports already opens com.sun.glass.ui.monocle to ALL-UNNAMED (src/test/addExports:12, tests/system/src/test/addExports:8).
- Keep the existing Java API shapes in the migration commit: LinuxSystem, EPDSystem, Udev and C lose the `native` keyword and delegate to LinuxSystemNative with unchanged signatures (long fd, long p, ByteBuffer + position/limit), so LinuxInputDevice, LinuxAbsoluteInputCapabilities, LinuxFrameBuffer, EPDFrameBuffer, MX6Cursor, AcceleratedScreen, EGLPlatform, X11AcceleratedScreen and LinuxSystemShim compile untouched (§2.4 'legacy long boundary' rule). loadLibrary() in LinuxSystem/EPDSystem becomes a facade touch (class init), never NativeLibLoader; the strings "glass_monocle" and "glass_monocle_epd" leave the tree. A second, separate commit may then move package-private callers to MemorySegment and drop C.Structure.
- Widths come from the linker, never from Java literals: request/count/offset/return types use LINKER.canonicalLayouts().get("long") / get("size_t") (FTNative.java:425 precedent); prot/flags/fd/whence/mode are JAVA_INT (the C casts them to int: LinuxSystem.c:55,62,67,299-300,153); void* is ADDRESS. All kernel structs in this lens (input_absinfo, fb_bitfield, fb_var_screeninfo, sockaddr_nl, the udev header, the mxcfb ints as Java models them) are __u32/__s32/__u16 and need no per-arch variant; the ioctl request encoding is the asm-generic one on x86, x86_64, arm and arm64 alike (asm-generic/ioctl.h:23-86). Pass ioctl requests zero-extended (Integer.toUnsignedLong).
- Variadic libc entry points get Linker.Option.firstVariadicArg: open(path, flags, mode) with firstVariadicArg(2) and ioctl(fd, request, arg) with firstVariadicArg(2). Binding them as fixed-arity would work by accident on aarch64 and be undefined on x86_64 (%al not set); the existing tree already uses firstVariadicArg for a variadic GTK call (GtkGlassNative.java:1690).
- errno is captured, not fetched: every fallible handle is created with Linker.Option.captureCallState("errno") and writes the value into a ThreadLocal that LinuxSystem.errno() / getErrorMessage() read, preserving the call-then-ask shape of EPDFrameBuffer.java:326-517 and LensUInput.java:234,269 with stronger guarantees than the two-transition JNI version.
- Memory: struct scratch for one ioctl lives in a try-with-resources confined arena; C.Structure-backed objects that outlive a call (screenInfo in LinuxFrameBuffer, updateData/syncUpdate in EPDFrameBuffer) get Arena.ofAuto() - the kernel copies the struct during the ioctl and retains nothing, so ofAuto() is safe here. mmap results are reinterpret(size)'d once in the facade and exposed as bounded MemorySegment with asByteBuffer() for Framebuffer; munmap takes the segment (or MemorySegment.ofBuffer(b).address() at the legacy boundary). Blocking downcalls (read on evdev, recv on netlink, MXCFB_WAIT_FOR_UPDATE_COMPLETE) are plain downcalls; nothing in this lens qualifies for Linker.Option.critical.
- Deletion scope for this lens: src/main/native-glass/monocle/linux/LinuxSystem.c (312 lines), linux/Udev.c (188), epd/EPDSystem.c (274), util/C.c (55). Monocle.h (37) and C.c's monocle_returnInt/Long go when x11/X11.c (their last user) is handled by the X11/EGL lens, or all of native-glass/monocle goes in one commit since no CMake target compiles any of it (native/linux.cmake:148-184) - either is build-neutral; the choice is about review granularity.
- Behaviour changes to schedule as separate, named commits after the migration lands: (1) MAP_FAILED check against -1L instead of 0xffffffffL (LinuxSystem.java:247; LinuxFrameBuffer.java:156; EPDFrameBuffer.java:635); (2) nl_pid = 0 instead of getpid() in the netlink bind (Udev.c:114); (3) strerror_r instead of strerror; (4) EPDInputDeviceRegistry.java:142-143 opens a fd it never closes; (5) LinuxSystemShim delegation bugs (setenv(value, value, ...), write(fd, buf, limit, limit), ioctl(fd, request, fd)) that make the tests/system LensUInput path non-functional; (6) MxcfbUpdateData models alt_buffer_data.virt_addr (a void* in NXP's mxcfb.h) as a 32-bit int (EPDSystem.java:465-466,587-588) - correct only on 32-bit i.MX; if a 64-bit EPD target ever appears the struct size, and therefore MXCFB_SEND_UPDATE's encoded size, change.
- Keeping Monocle also needs a packaging decision outside this lens: the Linux jar profile excludes com/sun/glass/ui/monocle/** (pom.xml:444-475, maven-jar-plugin), so the classes compile and are visible to tests through the shims module path but do not ship; a JNI-free Monocle is only useful if that exclusion is lifted (upstream ships Monocle in the Linux graphics jar).

### Open questions

- Is 32-bit armv7 still a Monocle target? JDK 26's Linker.nativeLinker() is implemented for x64, aarch64, riscv64, ppc64le and s390x; a 32-bit arm JDK reaches FFM only through the libffi fallback linker if that JDK build enables it, and none of the mainstream JDK 21+ distributions ship linux-arm32. If armv7 is dropped, canonicalLayouts still keeps the code honest but off_t/lseek64 questions and the 32-bit-only encodings (MAP_FAILED 0xffffffff, MxcfbUpdateData's int virt_addr) become dead concerns to clean up rather than preserve.
- Which EPD devices are in scope? EPDSystem's mxcfb layouts (MxcfbUpdateData 17 ints = 68 bytes with virt_addr as int; EPDSystem.java:452-476) match NXP's 32-bit i.MX6 SoloLite/6SLL mxcfb.h (Kobo devices named in EPDFrameBuffer.java:304-312,599-625). mxcfb.h is not in the WSL clone or /usr/include (find found none), so the 64-bit shape of struct mxcfb_alt_buffer_data (void* virt_addr) is asserted from NXP's header, not read here.

The I_FLUSH ioctl (STREAMS, LinuxSystem.java:218-222) is not supported on Linux at all and only ever returned an error.
- Sequencing with the X11/EGL lens: util/C.c's monocle_returnInt/Long and Monocle.h are used by x11/X11.c; delete the whole native-glass/monocle tree in one commit (nothing builds it) or per lens?
- Should the migration commit already fix the LP64 MAP_FAILED comparison (it changes observable behaviour: a failed mmap of /dev/fb0 today silently yields a bogus ByteBuffer), or land it as the first follow-up with its own test as the design list proposes?
- Packaging: lift the com/sun/glass/ui/monocle/** exclusion in the jar-excludes-linux profile (pom.xml:444-475) so a JNI-free Monocle actually ships on Linux, and if so, should it also ship in the Windows/mac jars (upstream excludes it there) where only the Headless/VNC platforms could run?

### Summary

### Design

- Three facades, no C: com.sun.glass.ui.monocle.XNative (libX11.so.6), EglNative (libEGL.so.1 + libGLESv2.so.2) and EglVendorNative (the -Dmonocle.egl.lib library implementing the do* contract). Each is a `final class` holding the Linker, its SymbolLookup(s), `static final` MethodHandles invoked with invokeExact, and its StructLayouts; every restricted call (libraryLookup, downcallHandle, reinterpret) stays inside them - the module already runs with --enable-native-access=javafx.graphics (pom.xml:349-356), and monocle peers keep calling package-private statics.
- Library lifetime = process lifetime: open libX11/libEGL/libGLESv2/vendor with SymbolLookup.libraryLookup(soname, Arena.global()), matching the JNI era that dlopen'ed and never dlclose'd (LinuxSystem.dlclose has no monocle caller). Try the versioned soname first (libEGL.so.1, libGLESv2.so.2, libX11.so.6) and fall back to the dev name the C used ('libEGL.so', 'libGLESv2.so', AcceleratedScreen.java:158-163), raising UnsatisfiedLinkError with the same messages ('Error loading libGLESv2.so', 'Error loading libEGL.so', 'EGLPlatform failed to load the requested library <lib>').
- RTLD_GLOBAL is a behaviour, not a lookup: keep a libc dlopen(path, RTLD_LAZY|RTLD_GLOBAL) before the libraryLookup of the vendor library (and, behind a property, of libEGL/libGLESv2) exactly as GtkGlassNative.Loader does (GtkGlassNative.java:5632-5645), because Gluon's libgluon_drm and vendor EGL blobs were written for a process where GLES symbols are in the global scope. FFM itself needs none of it: JavaFX's own egl*/do*/gl* references become explicit lookups.
- No upcalls in this lens: X11.c, EGL.c, eglBridge.c, the dispman/mx6 C and MonocleGLFactory.c contain no Call*Method, no cached IDs, no global refs and no AttachCurrentThread, so there is no callback table, no registry and no stub arena to design. XNextEvent is the only long-blocking call (X11 Input thread) and, like every X/EGL call here, must not be Linker.Option.critical.
- Struct handling: replace C.Structure (direct ByteBuffer + raw address, C.java:55-77) with MemorySegments from a definite arena - per-constructor Arena.ofConfined for X11Screen's XSetWindowAttributes and ClientMessage XEvent (X11Screen.java:61-146, closed at the end of the constructor); one XEvent segment per X11 Input thread from an Arena.ofConfined created inside that thread (X11InputDeviceRegistry.java:67-91); XColor goes away because X11.c:276-286 never read it. Layouts: XSetWindowAttributes 112 bytes (event_mask@72, override_redirect@88, cursor@104), XEvent 192 = sequenceLayout(24, JAVA_LONG) with named views (type@0, xany.window@32, xbutton.button@84, xmotion.x@64/y@68, xclient.message_type@40/format@48/data.l[i]@56+8i), XColor 16 - all LP64 from Xlib.h in the WSL Ubuntu (286-302, 404-411, 571-585, 589-603, 893-906, 930-936, 1004).
- Data model guard: XEvent's 'long pad[24]' is 192 bytes only where C long is 8; armv6hf (the only historic Monocle target) was ILP32 with 96-byte XEvents and 4-byte XIDs. Read LINKER.canonicalLayouts().get('long').byteSize() at class init and either refuse != 8 with an UnsatisfiedLinkError naming the reason (FTNative.load, FTNative.java:426-430 - recommended, since the fork has no ILP32 target) or build both layout sets. EGL native types are safe either way: EGLNativeWindowType is Window (XID) or khronos_uintptr_t and EGLNativeDisplayType is Display* or void* (eglplatform.h:106-118) - one integer-class register on LP64 SysV, bound as JAVA_LONG and ADDRESS respectively.
- Handles stay `long` at the peer boundary (rule 4): AcceleratedScreen.eglDisplay/eglSurface/eglContext/nativeWindow (AcceleratedScreen.java:36-39) and NativeScreen.getNativeHandle() are read across classes and by prism; convert once inside the facade (MemorySegment.ofAddress). The one API to change is AcceleratedScreen.getGLHandle() (AcceleratedScreen.java:176-178): it returned a dlopen handle for MonocleGLFactory.c's dlsym loop; replace it with a SymbolLookup (or a proc-address function) consumed by the ES2 lens's factory design.
- Behaviour-neutral migration commit, quirks preserved: XCreateBitmapFromData always 1x1 (X11.c:266-274); XCreatePixmapCursor ignores fg/bg/x/y (276-286); eglCreateContext ignores shareContext/attribs and hard-codes EGL_CONTEXT_CLIENT_VERSION 2 (EGL.c:176-180); _eglCreateWindowSurface passes NULL attribs (163-165); the static single eglWindowSurface (EGL.java:33, 181-191); the swap-failed-recreate-surface retry (AcceleratedScreen.java:189-201); EGLAcceleratedScreen skipping initPlatformLibraries (EGLAcceleratedScreen.java:45-56 via AcceleratedScreen():63); the -1 config sentinel (EGLAcceleratedScreen.java:51). The one deliberate divergence, documented in the commit: eglChooseConfig copies back numConfigs entries instead of configSize (EGL.c:146 read uninitialised malloc beyond numConfigs; the only caller uses configSize 1).
- setEGLAttrs (EGL.c:49-86) is the only PURE logic with a parity obligation: port it to a package-private static int[] in EglNative preserving the GLPixelFormat.Attributes index order (GLPixelFormat.java:58-66), the 5/6/5/0 -> EGL_BUFFER_SIZE 16 Raspberry Pi case and EGL_RENDERABLE_TYPE = EGL_OPENGL_ES2_BIT (0x0004 - add the constant to EGL.java), and prove PARITY: exact against a golden captured from the C (see testing).
- Vendor contract: replace egl_ext.h (jni.h, jlong/jint/jboolean/jfloat/jbyte*) with monocle_egl_ext.h using int64_t/int32_t/uint8_t/float/const uint8_t* - same widths on LP64, so an already-built libgluon_drm keeps working; keep egl_ext.h for one release as a thin alias that #includes the new header, then delete. Document the 24 symbols and the call order EGLAcceleratedScreen/EGLScreen/EGLPlatform/EGLCursor rely on; this header is the fork's only Monocle-EGL deliverable to third parties.
- Deletions in their own commits, before the ports so the port diffs shrink: (1) Dispman - 3 C files + wrapped_bcm.h + DispmanPlatform/PlatformFactory/Screen/Cursor/AcceleratedScreen; (2) MX6 - mx6/MX6AcceleratedScreen.c + MX6AcceleratedScreen/Platform/PlatformFactory/Cursor; (3) OMAP/OMAPX11 (pure Java); (4) EGL.java's six bodiless natives and EGL.c's JNI_OnLoad_glass_monocle; (5) native-prism-es2/monocle/eglUtils.c/.h + eglWrapper/ (dead: undefined LENSPORT symbols); (6) DEFAULT_PLATFORM_ORDER 'MX6,OMAP,Dispman,X11,Linux,Headless' -> 'X11,Linux,Headless' (NativePlatformFactory.java:70) with NativePlatformFactoryTest updated in the same commit. Then port X, then EGL.java, then the eglBridge contract.
- Generated-header hygiene (concurrent-native-build memory): X.java's 44 natives, EGL*.java's 38 and MonocleGLContext's @Native field (MonocleGLContext.java:33) all still make javac -h emit headers under target/gensrc/headers; nothing built includes them, but remove natives and @Native together and check the gensrc directory before declaring a class JNI-free. No CMake change is needed for anything in this lens - it ends with zero Monocle C - so the jfx-graphics-native skill's 'a linux.cmake target is a prerequisite for touching monocle' (SKILL.md:44) no longer applies to X11/EGL; only an EGL-flavoured prism_es2 (ES2 lens) would need a target.
- Testability drives the keep list: X11 is the one Monocle backend runnable in this fork's WSL under the rootless Xvfb recipe, and Mesa's libEGL.so.1 in WSL can exercise EglNative on the surfaceless/X11 platform; EGL-over-DRM needs a stub vendor library. Dispman and MX6 have no test path at all here, which is the second reason (after hardware obsolescence) to delete rather than port them.

## Monocle ES2 versus the prism_es2 FFM ABI

### Summary

Monocle's ES2 glue is already almost entirely Java: MonocleGLContext.makeCurrent and MonocleGLDrawable.swapBuffers never touch prism_es2 (they call AcceleratedScreen.enableRendering / swapBuffers, MonocleGLContext.java:52-58, MonocleGLDrawable.java:50-64), MonocleGLPixelFormat and MonocleGLDrawable never create a PixelFormatInfo or DrawableInfo, and the single JNI function that matters, MonocleGLFactory.nPopulateNativeCtxInfo (monocle/MonocleGLFactory.c:66-223), is malloc(ContextInfo) + four glGetString + 50 dlsym on the libGLESv2 handle Java opened + initState. Everything else in MonocleGLFactory.c returns constants (nGetAdapterOrdinal 0, nGetAdapterCount 1, nGetDefaultScreen 0, nGetDisplay 0, nGetVisualID 0, MonocleGLFactory.c:230-273) or reads a field that is never written (nGetIsGL2 -> ctxInfo->gl2, which initializeCtxInfo memsets to 0 and nPopulateNativeCtxInfo never sets: MonocleGLFactory.c:280-283, GLContext.c:63-69 - so Monocle always ran as GLES2). nInitialize (MonocleGLFactory.java:37) has no C body anywhere, which makes monocle/eglUtils.c (eglContextFromConfig, the dummy/shared window surfaces, printConfig*) and eglWrapper/* (whose PrismNativePort / LENSPORT_LIBRARY_NAME / NATIVE_PRISM_PORT_VERSION are defined nowhere in the tree: eglWrapper.c:71,105,121) dead code that cannot even compile here. The smallest ABI extension is therefore ONE new export, es2_context_adopt, that builds a render ContextInfo for a context the caller already made current and resolves the 50 entry points of the existing es2_proc_table (prism_es2_api.c:199-263) through a caller-supplied loader, plus a library-name choice in ES2Native (today hard-wired to "prism_es2", ES2Native.java:101, while ES2Pipeline.java:46-59 already expects "prism_es2_monocle" under -Dglass.platform=Monocle). The clean build shape is a separate prism_es2_monocle CMake target compiling only the generic sources with -DLINUX -DIS_EGLFB and linking GLESv2 only; one libprism_es2.so serving GLX and EGL is not viable because PrismES2Defs.h changes the ContextInfo / DrawableInfo / PixelFormatInfo layouts and several code paths at compile time under IS_EGL, and the desktop library's DT_NEEDED libGL/libX11 would fail to load on a board that has neither. MonocleGLContext's @Native field is the last thing in com.sun.prism.es2 that will force a javac -h header once MonocleGLFactory's eight natives are gone; today both com_sun_prism_es2_MonocleGLFactory.h and com_sun_prism_es2_MonocleGLContext.h are emitted, and the only consumer of the latter (MonocleGLFactory.c:37) uses nothing from it.

### Design

- ABI extension (prism_es2_api.h, ES2_ABI_VERSION 2u -> 3u at :124, ES2Native.ABI_VERSION 2 -> 3): `typedef void* (*Es2ProcLoader)(void* user, const char* name);` and `PRISM_ES2_EXPORT void* es2_context_adopt(Es2ProcLoader loader, void* user);` Contract: the caller has made its own GL/GLES context current on the calling thread; the function returns a render ContextInfo* whose driver strings are captured from that context and whose 50 entry points (the es2_proc_table rows, prism_es2_api.c:199-257) are loader(user, name) (NULL allowed, as before), with initState run and state.vSyncEnabled/vSyncRequested left 0 (Monocle never applied a swap interval: MonocleGLContext has no vsync path). context/egldisplay/display stay NULL and gl2 stays 0. Returns NULL (stderr line) when loader is NULL, malloc fails or glGetString(GL_VERSION) is NULL - the last is the one deviation from nPopulateNativeCtxInfo, which would have crashed. es2_context_release on the result frees the strings only (Java owns the EGL context). es2_context_get_string and es2_context_get_proc_address work on it unchanged. Optional zero-upcall variant if the review prefers it: `void* es2_context_adopt_dl(void* dl_handle)` with C doing dlsym(dl_handle ? dl_handle : RTLD_DEFAULT, name), which is literally MonocleGLFactory.c:114-219 minus JNI; it hard-wires dlsym, so the callback form is proposed as primary and the Java stub does exactly that dlsym for the migration commit, leaving an eglGetProcAddress fallback to a later behaviour commit.
- Java side (behaviour-neutral flip): MonocleGLFactory.initialize keeps its shape (MonocleGLFactory.java:93-141) and replaces line 119 with `nativeCtxInfo = ES2Native.contextAdopt(loaderStub, glHandle)` between accScreen.enableRendering(true) and (false); the stub is a `Linker.upcallStub` created in ES2Native (restricted methods stay in the FFI class) over a static `(MemorySegment user, MemorySegment name) -> MemorySegment` that calls the monocle FFI class's dlsym binding on `user.address()` (0 -> RTLD_DEFAULT), catches Throwable and returns MemorySegment.NULL; its arena is a confined arena scoped to the adopt call, which is legal because C stores the resolved pointers, never the loader. gl2 = false, getAdapterCount() = 1, getAdapterOrdinal() = 0, the five unused native declarations and nInitialize deleted, the @Native annotation and import dropped from MonocleGLContext (MonocleGLContext.java:28,33). MonocleGLContext.getNativeHandle keeps returning 0L (MonocleGLContext.java:47-49; es2_context_get_native_handle would also return 0 on the adopted struct).
- Make-current and swap keep routing back to Java's AcceleratedScreen, unchanged: ES2Context calls glContext.makeCurrent(drawable) -> MonocleGLContext.makeCurrent -> accScreen.enableRendering(true/false) (ES2Context.java:87, MonocleGLContext.java:52-58) which is EGL.eglMakeCurrent on the Java-created context (AcceleratedScreen.java:142-149); ES2SwapChain's drawable is a MonocleGLDrawable whose swapBuffers calls accScreen.swapBuffers() then glCtx.clearBuffers (MonocleGLDrawable.java:50-64, AcceleratedScreen.java:189-201). No es2_context_make_current / es2_drawable_swap_buffers / es2_pixel_format_create / es2_drawable_create call is made on Monocle (MonocleGLPixelFormat and MonocleGLDrawable never set nativePFInfo / nativeDrawableInfo), so the stubbed lifecycle exports in prism_es2_api_monocle.c are never reached; they exist only so ES2Native's eager bind succeeds. The prerequisite is that EGL.java's nine live natives and LinuxSystem.dlopen/dlsym (LinuxSystem.java:236-239) are FFM by then (EglNative over libEGL.so, libc dlopen/dlsym or SymbolLookup.libraryLookup), otherwise AcceleratedScreen cannot create the context es2_context_adopt adopts.
- CMake: a separate `prismES2Monocle` target in linux.cmake next to prismES2 (linux.cmake:169-177): `add_jfx_library(prismES2Monocle OUTPUT_NAME prism_es2_monocle SOURCE_DIRS native-prism-es2 native-prism-es2/GL native-prism-es2/monocle COMPILE_OPTIONS -DLINUX -DIS_EGLFB ${JFX_C_STRICT_OPTIONS} LINK_LIBS PkgConfig::GLESV2)` guarded by a new `option(INCLUDE_ES2_MONOCLE ... OFF)` (or ON when `pkg_check_modules(GLESV2 glesv2)` succeeds), no x11/ directory, no X11, no GL, no EGL link, no HEADERS_DIR / JDK include (like prismES2 today, linux.cmake:143-146). native-prism-es2/GL holds headers only, so the glob adds no sources; native-prism-es2/monocle holds only the new prism_es2_api_monocle.c after eglUtils.* and eglWrapper/ are deleted (eglWrapper/ must go or be excluded: SOURCE_DIRS glob non-recursively, so simply not listing it also works). The desktop prismES2 target is untouched. -lGLESv2 is what removes the JNI-era dependence on Java's RTLD_GLOBAL dlopen order; the build host needs Mesa's libgles2-mesa-dev (WSL Ubuntu has it), a board build needs its vendor libGLESv2.so at link time or `-Wl,--unresolved-symbols=ignore-in-shared-libs` plus keeping AcceleratedScreen's RTLD_GLOBAL dlopen, which is the JNI-era arrangement and is documented here as the fallback, not the default.
- Why not one libprism_es2.so for GLX and EGL: PrismES2Defs.h is compile-time bimodal (IS_GLX vs IS_EGL at :35-39) and it changes struct layouts (ContextInfo :174-191 GLXContext vs EGLContext plus screen/visualID; DrawableInfo :129-137; PixelFormatInfo :105-110), the renderbuffer, MSAA and polygon-mode code paths (GLContext.c:271-308,329-336; prism_es2_api.c:392-406,526,555) and the deleteCtxInfo branch (GLContext.c:104-109); a single binary would need both variants selected at run time inside every function, and its DT_NEEDED libGL.so.1 / libX11.so.6 (linux.cmake:176) make the dynamic loader refuse it on a board with neither. The separate target also matches the library name ES2Pipeline already expects (ES2Pipeline.java:54) and the JNI-era layout the skill records (jfx-graphics-native SKILL.md:44: monocle was built only by the embedded Gradle targets this fork dropped). Verdict: separate prism_es2_monocle target, generic sources only, -DIS_EGLFB, GLESv2 link, GL entry points resolved at run time through es2_context_adopt.
- Header hygiene under IS_EGLFB so the target compiles with no X11/GLX/EGL dev packages: guard PrismES2Defs.h:43-46 (X11 + glx includes) and :59-62 (EGL + eglWrapper includes) with #ifndef IS_EGLFB; under IS_EGLFB make ContextInfo.display / DrawableInfo egl members void* or drop them, drop glxExtensionStr and glXSwapIntervalSGI (:212-214) and guard the ES2_PROC(glXSwapIntervalSGI) row (prism_es2_api.c:260-262) with !defined(IS_EGL); remove GLContext.c:107-109. The tree's own GL/gl.h + GL/glext.h keep supplying the prototypes and PFNGL* typedefs (the JNI-era monocle build also compiled desktop GL headers against a GLES library; the IS_EGL ifdefs exist precisely for the GLES-only differences).
- Deletions in the same change set as the Java flip (the C build only passes on stale headers otherwise): native-prism-es2/monocle/MonocleGLFactory.c, eglUtils.c, eglUtils.h, native-prism-es2/eglWrapper/eglWrapper.c, eglWrapper.h, and target/gensrc/headers/javafx.graphics/com_sun_prism_es2_MonocleGLFactory.h + com_sun_prism_es2_MonocleGLContext.h (stale copies; javac -h at pom.xml:219-243 stops emitting them once the natives and the @Native are gone). ### Open questions

- Loader shape: callback es2_context_adopt(Es2ProcLoader, void*) (one export, Java can later add an eglGetProcAddress fallback without touching C) versus es2_context_adopt_dl(void* dl_handle) (zero upcalls, exact JNI body, hard-wires dlsym in prism_es2) versus a caller-filled 50-pointer table with es2_proc_count/es2_proc_name (three exports, no upcall, Java owns resolution). The write-up proposes the callback; a decision is needed before the ABI bump.
- Link -lGLESv2 into prism_es2_monocle (removes the RTLD_GLOBAL load-order dependency; needs Mesa GLESv2 dev files on the build host and a vendor libGLESv2 at cross-link time) or keep the JNI-era arrangement (unresolved gl* symbols bound lazily against Java's RTLD_GLOBAL dlopen of libGLESv2.so)? Routing the 25 direct gl* calls through the table would remove the question entirely but touches every generic function.
- Once LinuxSystem.dlopen/dlsym become FFM, should AcceleratedScreen keep dlopen(RTLD_LAZY|RTLD_GLOBAL) of libGLESv2.so / libEGL.so through a libc binding (exact parity, needed if vendor GLES stacks depend on global symbol scope) or switch to SymbolLookup.libraryLookup (no RTLD_GLOBAL)? Also whether to keep the -dev symlink names libGLESv2.so / libEGL.so (AcceleratedScreen.java:158,163) or fall back to the .so.2 sonames boards actually ship - a behaviour change for a later commit.
- Is the LENSPORT / PrismNativePort mechanism (eglWrapper.c) confirmed dead for every board the user cares about? Nothing in this tree defines it, so deleting it is the only option that compiles, but it was the vendor hook of the Lens era.
- egl_ext.h is a vendor-facing contract (JNI-typed externs the monocle.egl.lib library implements). Binding those symbols directly keeps the names and scalar widths; is dropping the jni.h include from the shipped header acceptable to the user's embedded partners, or should the header be kept verbatim as documentation?

### Design

- (a) Libraries after the migration: glass side NONE - libglass_monocle.so, libglass_monocle_x11.so, libglass_monocle_epd.so (never built by this fork: linux.cmake:148-185 defines only glassgtk3, prismSW, prismES2, iio) are replaced by Java bindings to libc (Linker.nativeLinker().defaultLookup(), pattern GtkGlassNative.java:163), libX11.so.6 and libEGL.so (SymbolLookup.libraryLookup in Arena.global(), pattern GtkGlassNative.java:90-95 / FTNative.java:431), the -Dmonocle.egl.lib vendor library, libbcm_host.so and two dlsym'd Vivante pointers. - (a) linux.cmake change: exactly one new block, add_jfx_library(prismES2Monocle OUTPUT_NAME prism_es2_monocle SOURCE_DIRS "${GRAPHICS_SRC}/native-prism-es2" "${GRAPHICS_SRC}/native-prism-es2/GL" "${GRAPHICS_SRC}/native-prism-es2/monocle" COMPILE_OPTIONS -DLINUX -DIS_EGLFB ${JFX_C_STRICT_OPTIONS} LINK_LIBS PkgConfig::EGL) with pkg_check_modules(EGL IMPORTED_TARGET egl glesv2) and a new option INCLUDE_MONOCLE_ES2 plumbed from the pom like INCLUDE_ES2 (pom.xml:790, CMakeLists.txt:47-51). No HEADERS_DIR/JDK include for the target: it has no JNI.
- (a) Facade placement: keep LinuxSystem, X, EGL and C as the binding classes (they are already the package's only native holders, singletons with package-private APIs used from 15+ classes) but make them the fork's `*Native`-style facades: static final MethodHandles, invokeExact, all restricted calls (nativeLinker, libraryLookup, reinterpret) inside them, no restricted call in peers - a documented naming deviation from the ES2Native/GtkGlassNative convention justified by the ~40 call sites and the shims (LinuxSystemShim) that already name them. C.Structure keeps (ByteBuffer b, long p) in the first pass so the 8 structure subclasses compile unchanged; field access moves from native getters to VarHandles over MemorySegment.ofAddress(p).reinterpret(sizeof).
- (a) Layout/ABI rules for embedded targets: kernel UAPI structs Monocle touches are fixed-width (fb_var_screeninfo 40 x u32 = 160, input_absinfo 6 x s32 = 24, sockaddr_nl 12, udev headers 24) and identical on x86-64/aarch64/armhf; the arch-dependent ones are input_event (24 LP64 / 16 ILP32 - LinuxEventBuffer.EventStruct64Bit/32Bit already encode both, LinuxEventBuffer.java:40-63), the Xlib structs (XEvent 24 C longs = 192/96, XSetWindowAttributes 112 LP64, XColor 16/12) and every pointer-typed EGL handle. Select variants on ValueLayout.ADDRESS.byteSize() and take C `long`/off_t/size_t from Linker.nativeLinker().canonicalLayouts(). ioctl numbers are computed in Java with the asm-generic _IOC layout (x86, arm, aarch64 share it; mips/ppc/alpha do not - out of scope, note it). Variadic libc functions (ioctl, open) use Linker.Option.firstVariadicArg.
- (a) Monocle is downcall-only: the C never calls Java (grep of the monocle C for Call*Method/GetMethodID/AttachCurrentThread: none; Udev.run, X11InputDeviceRegistry's XNextEvent loop and LinuxInputDevice.run are Java threads).
